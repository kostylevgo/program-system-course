# 8. Типы классов

| Класс | Тип | Обоснование |
| --- | --- | --- |
| Ежедневник | Entity | Два журнала могут иметь одинаковую подпись пациента, но оставаться разными наборами записей; различаются идентификаторами по A6 |
| Рецепт | Entity | Два полученных рецепта могут иметь одинаковые дату, врача, болезнь и схемы, но представлять разные зарегистрированные документы; исправление сведений не меняет идентичность записи |
| Назначение | Entity | Две одинаковые строки в разных рецептах различимы по происхождению и своим событиям; до планирования содержимое можно исправить без замены идентичности |
| ПриёмЛекарства | Entity | Это отдельное событие плана; отметка и сброс меняют состояние того же события. У двух назначений могут быть одинаковые время и статус, но разные приёмы |

Все классы отмечены `<<Entity>>` в итоговой диаграмме. Устойчивые идентификаторы введены явно в A6, а не выведены из исходной фразы.

Дополнительные типы не требуются:

- **Value-object:** простые значения представлены встроенными типами. Для отдельного `Лекарство` или `Болезнь` нет достаточного обоснования по СИАОУТ. Неизменяемость значения сама по себе не даёт критерии И и О.
- **Service:** план строится по данным одного назначения, поэтому операция находится у него.
- **Repository:** доменный журнал содержит свои записи и предоставляет цель предметной области — просмотр приёмов по дате. Это не абстракция доступа к внешнему хранилищу и не каталог независимых сущностей. Хранение в БД заданием не определено.
- **Factory:** создание собственных частей — естественная ответственность владельцев; отдельный объект для сложного создания не нужен.

Несовместимого совмещения ответственностей не выявлено. Наличие коллекции не превращает Entity автоматически в Repository, а создающая операция — в Factory.
