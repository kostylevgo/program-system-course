# 5. Атрибуты, методы и связи

## Судьба исходных и отложенных понятий

| Понятие | Элемент модели | Обоснование |
| --- | --- | --- |
| Больной, посетитель, пациент | `Ежедневник.пациент` | Синонимы одной роли, R1–R2, A1; отдельный класс не прошёл этап 4 |
| Доктор, врач | `Рецепт.врач` | Обозначение автора, R1, A2 |
| Болезнь, заболевание | `Рецепт.болезнь` | Причина назначения в рамках одного рецепта, R1, A2 |
| Лекарство | `Назначение.лекарство` | Текстовое обозначение, R1–R2, A3; доза принадлежит назначению, а не препарату |
| Рецепт на лекарства | `Рецепт` и композиция `содержитНазначения` | Один рецепт может описывать несколько разных схем, A3 |
| Посещение врача | Не отражается отдельным элементом | Внешний контекст R1, система не ведёт визиты |
| Получение рецепта | Внешнее действие; затем `Ежедневник.записатьРецепт` | Запись сведений отличается от медицинской выписки, A2 |
| Приём лекарств | `ПриёмЛекарства` и операции отметки | Разовое событие отделено от процесса и от схемы, R2, A4–A5 |
| Построение расписания | `Назначение.составитьПлан` | Процесс владеющего схемой объекта, A4; отдельный Service не требуется |
| Доза, даты, времена, статус | Атрибуты ниже | Значения, а не самостоятельно учитываемые сущности |
| Программа, метод, класс, модель | Граница системы и методика решения | Метапонятия R2–R3, не сущности предметной области |

## Атрибуты

Все атрибуты закрыты для произвольного изменения. `Идентификатор`, `Текст`, `Дата`, `Время`, `ДатаВремя`, `Множество<Время>` — типы значений, не дополнительные классы предметной области.

| Класс | Атрибуты | Источник |
| --- | --- | --- |
| Ежедневник | `id: Идентификатор`, `пациент: Текст` | R2, A1, A6 |
| Рецепт | `id: Идентификатор`, `датаВыдачи: Дата`, `врач: Текст`, `болезнь: Текст` | R1, A2, A6 |
| Назначение | `id: Идентификатор`, `лекарство: Текст`, `доза: Текст`, `начало: Дата`, `конец: Дата`, `времена: Множество<Время>` | R1–R2, A3–A4, A6 |
| ПриёмЛекарства | `id: Идентификатор`, `плановоеВремя: ДатаВремя`, `статус: Текст`, `фактическоеВремя: ДатаВремя [0..1]` | R2, A4–A6 |

Доза хранится вместе с единицей, например как текст; модель не вычисляет дозировку. Статус ограничен тремя значениями из A5. Связи не дублируются полями внешних ключей: это концептуальная модель, не схема БД.

## Операции и контракты

В диаграммах аргумент `данные` сокращает перечисление значений из этой таблицы; это не скрытый доменный класс. Передача данных не предполагает интерфейс пользователя или формат API.

| Класс и операция | Данные и результат | Контракт |
| --- | --- | --- |
| `Ежедневник.записатьРецепт(данные): Рецепт` | Дата, врач, болезнь и непустой набор данных назначений | Проверить данные и атомарно создать рецепт с назначениями, присоединить к этому ежедневнику; частично пустой рецепт не публикуется |
| `Ежедневник.приёмыНаДату(дата): ПриёмЛекарства[0..*]` | Дата → события с лекарством, дозой и статусом, доступными через связи | Пройти по своим рецептам и назначениям, отфильтровать по локальной дате планового времени, отсортировать по времени; не менять состояние |
| `Рецепт.уточнитьРеквизиты(данные): void` | Дата, врач, болезнь | Исправить только реквизиты локальной записи; не менять назначения и их события |
| `Рецепт.добавитьНазначение(данные): Назначение` | Лекарство, доза, начало, конец, времена | Проверить схему, создать новое назначение без приёмов, связать с этим рецептом |
| `Назначение.исправить(данные): void` | Лекарство, доза, начало, конец, времена | Допустимо только при отсутствии приёмов; проверить новую схему до замены |
| `Назначение.составитьПлан(): ПриёмЛекарства[0..*]` | Возвращает полный текущий набор своих событий | Для всех дней курса включительно и времён создать отсутствующие события со статусом `запланирован`; сохранить существующие идентификаторы и отметки |
| `ПриёмЛекарства.отметитьПринятым(время): void` | Фактическое локальное время | Только из `запланирован`: статус → `принят`, факт → переданное время |
| `ПриёмЛекарства.отметитьПропущенным(): void` | Без аргументов | Только из `запланирован`: статус → `пропущен`, факт остаётся пустым |
| `ПриёмЛекарства.сброситьОтметку(): void` | Без аргументов | Из любого статуса: статус → `запланирован`, факт → пусто; смена одной отметки на другую делается через сброс |

Схема корректна, когда обязательные тексты непусты, `начало ≤ конец`, множество времён непусто и содержит допустимые значения времени суток. Эти проверки не оценивают медицинскую обоснованность.

## Связи, роли и кратности

Роль — имя конца связи; кратность у конца B показывает количество B для одного A. Каждая композиция допускает навигацию к частям и к владельцу.

| Имя связи | Тип | Конец A: класс / роль / кратность | Конец B: класс / роль / кратность | Обоснование |
| --- | --- | --- | --- | --- |
| `хранитРецепты` | Композиция | Ежедневник / `ежедневник` / 1 | Рецепт / `рецепты` / 0..* | Новый журнал может быть пуст; локальная запись рецепта принадлежит ровно одному журналу, A2, A8 |
| `содержитНазначения` | Композиция | Рецепт / `рецепт` / 1 | Назначение / `назначения` / 1..* | Записанный рецепт создаётся сразу с непустым набором строк; строка не разделяется между рецептами, A3, A8 |
| `планируетПриёмы` | Композиция | Назначение / `назначение` / 1 | ПриёмЛекарства / `приёмы` / 0..* | До построения плана событий нет; каждое событие относится к одной схеме, A4, A8 |

Кратности заданы проектными предположениями; исходный текст сам по себе всех их не устанавливает. Неустановленных кратностей внутри принятой модели не осталось. Срок жизни части ограничен сроком жизни записи-владельца. Пользовательских операций удаления нет; завершение хранения ежедневника означает завершение хранения его локальных записей. Это не удаляет оригинал рецепта и не обозначает исчезновение людей или лекарств.

Обобщений нет: ни одна пара принятых классов не находится в отношении «вид». Пустой ромб не используется: независимое разделяемое владение частями не требуется. Зависимости вызова операций отдельно не рисуются поверх уже существующих структурных связей.

## Ограничения, не выражаемые кратностями

- **C1.** Все части имеют одного композиционного владельца; перемещение и разделение запрещены.
- **C2.** Ключ события `(назначение, плановоеВремя)` уникален; разные назначения могут иметь одно время.
- **C3.** До планирования событий нет. После успешного `составитьПлан` для каждого дня курса существует по событию на каждое время из схемы. Число событий тогда равно числу дней включительно, умноженному на число времён; частично построенный план не публикуется.
- **C4.** Статус принадлежит `{запланирован, принят, пропущен}`; фактическое время задано тогда и только тогда, когда статус равен `принят`.
- **C5.** Назначение после появления хотя бы одного приёма неизменно; идентификатор и плановое время события неизменны.
- **C6.** Запись рецепта создаётся атомарно с ≥ 1 назначением. Удаление строк и истории не входит в интерфейс.
- **C7.** Просмотр даты определяется планом, даже если фактический приём произошёл в другую дату. Отметка пропуска не выводится из часов автоматически.
- **C8.** Повторное планирование не меняет существующие события; смена отметки требует сброса. Операции сохраняют C1–C7.

Связи обеспечивают получение пациента через цепочку `ПриёмЛекарства → Назначение → Рецепт → Ежедневник`, а лекарства и дозы — через назначение. Дублировать их в каждом событии не требуется благодаря C5.
