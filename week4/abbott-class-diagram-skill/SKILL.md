# Построение диаграммы классов методом Аббота

Выполни девять этапов ниже. Сохраняй промежуточные решения, включая отклонённые кандидаты, и связывай их с исходным текстом.

## Результат на диске

Подбери короткое содержательное имя папки по предметной области или основной задаче исходного текста. Используй строчные латинские буквы и дефисы. Создай папку с выбранным именем в текущей директории. Если имя уже занято, добавь числовой суффикс `-2`, `-3` и далее до свободного имени. Если в задаче явно задан путь результата, используй его.

Сохрани исходное описание в `00-source.md`, пронумеровав требования R1, R2, … для ссылок из артефактов. Проектные предположения обозначай отдельно от требований.

Обязательные файлы:

| Файл | Содержание |
| --- | --- |
| `00-source.md` | Исходный текст и нумерованные требования |
| `01-nouns.md` | Подходящие и неподходящие существительные |
| `02-filtering.md` | Синонимы, отложенные процессы и оставшиеся кандидаты |
| `03-actions.md` | Действия и их распределение по классам |
| `04-criteria.md` | Проверка каждого кандидата по С, И, А, О, У, Т |
| `05-relations.md` | Атрибуты, методы, именованные связи и роли |
| `06-draft.puml` | Черновая UML-диаграмма классов |
| `07-use-cases.puml` | UML-диаграмма вариантов использования |
| `07-coverage.md` | Сценарии, проверка их реализации и необходимые исправления |
| `08-class-types.md` | Тип каждого класса с обоснованием |
| `09-aggregates.md` | Агрегаты, корни и проверка условий либо обоснование, почему укрупнение не нужно |
| `final-class-diagram.puml` | Итоговая UML-диаграмма классов после всех проверок |

Используй PlantUML: он поддерживает обе требуемые разновидности UML-диаграмм. При доступном рендерере дополнительно сохрани SVG каждой диаграммы. Исходники `.puml` обязательны независимо от возможности рендеринга. В ответе дай ссылку на папку, итоговую диаграмму и перечисли нерешённые вопросы, если они остались.

## 1. Найди подходящие существительные

Разбирай существительные и именные словосочетания; приведи словоформы к начальной форме.

- Подходящие: вещи, роли, виды, родовые существительные. Они становятся кандидатами в классы.
- Неподходящие: абстрактные существительные, собирательные существительные, названия, местоимения. Название конкретного экземпляра не становится классом.

Для каждого термина запиши фрагмент текста, номер требования, категорию и решение. При неоднозначной классификации поясни выбранное значение.

## 2. Отфильтруй кандидатов

Объедини синонимы под одним именем, сохранив соответствие исходных терминов. Отложи существительные, обозначающие процесс или процедуру, в отдельный список для этапа 5.

В `02-filtering.md` запиши канонические имена, группы синонимов, отложенные процессы и список оставшихся кандидатов. Отложенные понятия не теряются: далее они могут стать методами, связями или основанием для Service.

## 3. Выдели действия

Найди глаголы, обозначающие действия, которые можно связать с одним из кандидатов в классы. Для каждого действия запиши требование, участников, владельца операции, затрагиваемое состояние и основание выбора владельца.

Распределяй действия по инкапсулируемым данным и ответственности, а не автоматически по грамматическому субъекту. Операцию размещай в классе, который управляет затрагиваемым состоянием.

Действия без подходящего владельца сохрани отдельно: вернись к ним при выделении методов и Service.

## 4. Проверь кандидатов по С, И, А, О, У, Т

| Критерий | Условие |
| --- | --- |
| С — состояние | У экземпляров класса есть состояние |
| И — интерфейс | Есть способ изменить состояние через интерфейс |
| А — атрибуты | Состояние сложное: содержит больше одного поля |
| О — операции | В интерфейсе больше одной операции |
| У — универсальность | Состояние и интерфейс подходят всем экземплярам класса |
| Т — существенное требование | Без этого класса модель не обеспечивает существенное требование |

Для каждого кандидата составь строку: **кандидат → С → И → А → О → У → Т → сумма → решение**. Для каждого критерия приведи конкретное обоснование: поля, операции, требование или контрпример. Используй значения «да», «нет», «не установлено»; в сумму входят только «да».

Правило принятия строгое: **Т = да ИЛИ сумма положительных критериев ≥ 4 из 6**. В остальных случаях кандидат не становится классом. Для Т укажи конкретное требование и объясни, почему без класса его нельзя обеспечить. Не добавляй поля и операции исключительно ради прохождения порога.

Сохрани отклонённые понятия для этапа 5. Если сведений недостаточно, отметь, что решение предварительное, и укажи недостающие данные.

## 5. Выдели атрибуты, методы и связи

Рассмотри устойчивые сочетания из текста, понятия, не прошедшие этапы 2 и 4, и действия этапа 3. Распредели их между атрибутами, методами и связями объектов. Для синонима укажи уже существующий элемент, а не создавай дубликат.

Для каждого преобразования запиши исходное понятие, новый элемент, класс-владелец или участников и обоснование. Если понятие не имеет самостоятельного отражения в модели, объясни исключение.

У каждого атрибута, метода и связи должно быть имя. Для связи укажи понятные роли участников, тип UML-связи и кратности на обоих концах. Кратность у конца B означает число объектов B для одного A. Неустановленные кратности явно отметь в таблице и примечании диаграммы.

Различай ассоциацию, обобщение, агрегацию, композицию и зависимость по смыслу отношения. Композицию обосновывай владением и жизненным циклом части, обобщение — отношением «вид». Отдельно запиши ограничения, не выражаемые кратностями.

## 6. Составь черновик диаграммы классов

В `06-draft.puml` отрази принятые классы, их атрибуты, операции, именованные связи, роли и известные кратности. Используй единые имена с таблицами предыдущих этапов.

Черновик сохраняет результат этапа 6; последующие исправления отражай в итоговой диаграмме и журнале изменений в `07-coverage.md`.

## 7. Составь use-case диаграмму и проверь покрытие

Выдели акторов и их цели из исходного текста. Построй `07-use-cases.puml` с границей системы, акторами и вариантами использования. Актор не обязан быть классом. `include` и `extend` используй только при наличии соответствующего смысла в сценариях.

В `07-coverage.md` опиши основные сценарии и заданные текстом альтернативы. Для каждого шага укажи **use case → шаг → класс и операция → используемые атрибуты и связи → результат или изменение состояния → покрыт/пробел**.

Проверь, что модель позволяет выполнить все действия сценариев. Для каждого пробела уточни владельца операции, необходимые данные и связи. Если нужен новый класс, проведи его через этапы 1–5 и критерии этапа 4. Сохрани изменения и повтори проверку. Неразрешимые без уточнения требований пробелы перечисли явно.

## 8. Укажи тип каждого класса

| Тип | Условие |
| --- | --- |
| Value-object | Экземпляры неразличимы, если совпадают все их атрибуты |
| Entity | Экземпляры различимы даже при совпадении их атрибутов |
| Service | Реализует процесс; состояния нет либо оно не относится к предметной области |
| Repository | Ведёт учёт экземпляров других классов |
| Factory | Создаёт экземпляры других классов |

Для каждого класса выбери тип и обоснуй его через идентичность или ответственность. Отметь тип стереотипом в итоговой диаграмме. Если класс совмещает несовместимые ответственности, раздели его с повторной проверкой критериев и use cases.

Service может не проходить критерии С и А: правило принятия остаётся прежним, включая возможность принятия по Т. Repository и Factory также требуют обоснования; наличие типов в перечне не означает, что они обязательно должны присутствовать в модели.

## 9. Укрупни модель

Если модель велика, сгруппируй связанные классы в агрегаты и выбери корень каждого агрегата. Размер оценивай по сложности связей и ответственности, а не по фиксированному числу классов.

Проверь два условия:

1. Все межагрегатные связи ведут в корень целевого агрегата.
2. Корень управляет всеми объектами своего агрегата; необходимые операции управления доступны через него.

В `09-aggregates.md` перечисли агрегаты, их состав, корни, операции управления и межагрегатные связи. Для каждой связи проверь целевой корень; для каждого внутреннего объекта — управление со стороны корня. Агрегат не равнозначен UML-агрегации с пустым ромбом.

Если укрупнение не требуется, всё равно создай файл с обоснованием. В итоговой диаграмме покажи границы выделенных агрегатов и отметь корни. Повтори проверку сценариев после изменения доступа к объектам.

## Итоговая проверка

- Созданы все обязательные файлы; решения каждого этапа можно проследить до исходных требований.
- Все итоговые классы прошли правило Т или ≥ 4 из 6, имеют тип и согласованы с таблицами.
- Каждое действие use cases реализуемо через операции и связи либо явно отмечено как нерешённый пробел.
- Связи названы, роли определены, известные кратности указаны.
- Для выделенных агрегатов выполнены оба условия этапа 9.
- Итоговая диаграмма включает исправления после черновика; все её участники объявлены, имена и синтаксис PlantUML согласованы.
