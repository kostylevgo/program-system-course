# Решение задания 5 5 о CRM

В модели выделены три актора, четыре варианта использования, пять сущностей и один сервис. Ниже приведён ответ на пункты а–в; подробное обоснование каждого решения сохранено в файлах этапов анализа.

## Акторы и варианты использования

| Актор | Варианты использования |
| --- | --- |
| Менеджер по продажам | Управление карточками клиентов ManageClients; обработка заявки ProcessNote; проведение сделки ConductDeal. |
| Клиент | Обработка заявки ProcessNote; проведение сделки ConductDeal. |
| Руководитель отдела | Подготовка отчёта PrepareReport. |

![Акторы и варианты использования CRM](07-use-cases.svg)

[Исходник диаграммы вариантов использования](07-use-cases.puml).

Акторы обозначают внешние роли по отношению к CRM. Менеджер не связан с подготовкой отчёта, а руководитель не наследует функции менеджера: такого расширения полномочий в условии нет. include и extend не используются, поскольку обязательные вызовы и условные расширения сценариев не описаны.

## Кандидаты по методу именных групп

Из текста получены карточка клиента, заявка, сделка, менеджер по продажам, руководитель отдела, клиент, отчёт, реквизиты, дата и время, текст сообщения, текст ответа, отдел. Заданные английские названия ClientCard, Note и Deal объединяются с соответствующими русскими понятиями.

| Кандидаты | Решение |
| --- | --- |
| Карточка клиента, заявка, сделка | Классы ClientCard, Note, Deal: самостоятельные учётные объекты. |
| Менеджер по продажам, руководитель отдела | Классы SalesManager, DepartmentHead: необходимо хранить назначения определённым сотрудникам. Также остаются акторами на другой диаграмме. |
| Клиент | Актор. Заданные сведения о нём хранятся в карточке; собственных данных для дополнительного класса Client пока нет. |
| Реквизиты | Атрибут ClientCard.requisites; структура реквизитов не задана. |
| Дата и время, сообщение, ответ | Атрибуты Note.submittedAt, messageText и replyText. |
| Отчёт | Результат операции, представленный текстом по предположению P4. Хранение и самостоятельная структура отчёта не заданы. |
| Отдел | Не выделяется: упомянут только в названии роли руководителя. |

Названия процессов — управление, обработка, проведение, подготовка — становятся вариантами использования и операциями. Для подготовки отчёта введён ReportService без собственного предметного состояния. Он принят по критерию существенного требования R4; это проектный выбор владельца процесса.

Полный список словосочетаний и исключений находится в [01-nouns.md](01-nouns.md) и [02-filtering.md](02-filtering.md). Проверка всех 13 кандидатов, включая сервис, по строгому правилу «Т либо минимум четыре положительных критерия» находится в [04-criteria.md](04-criteria.md).

## Модель предметной области

![Итоговая диаграмма классов CRM](final-class-diagram.svg)

[Исходник итоговой диаграммы классов](final-class-diagram.puml).

| Класс | Хранимое предметное состояние | Основные операции |
| --- | --- | --- |
| ClientCard | Реквизиты; связи с менеджером, заявками и сделками | Создание, updateRequisites, addNote, recordDeal. |
| Note | Дата/время и сообщение обязательны; ответ необязателен; связь с карточкой | setReply. |
| Deal | Отдельная идентичность сделки и связь с карточкой; подробные поля не заданы | Создание через ClientCard.recordDeal; собственные изменения не описаны. |
| SalesManager | Назначенные карточки и единственный руководитель | assignCard, assignHead. |
| DepartmentHead | Связь с подчинёнными менеджерами | getManagedCards — производный запрос для отчёта по P4. |
| ReportService | Предметное состояние не хранит | prepareReport. |

У пяти сущностей обозначен id по предположению P3. Это техническое представление идентичности, а не дополнительное требование к реквизитам или бизнес-данным.

Каждому менеджеру соответствует ровно один руководитель и несколько карточек. «Несколько» прочитано буквально как 2..*. Число менеджеров одной карточки не задано; в модели по P1 принят один. У карточки допускаются 0..* заявок и 0..* сделок; единственность карточки для каждой записи принята по P2. У руководителя число менеджеров не ограничено условием, поэтому по P7 выбрано 0..*.

Все четыре структурные связи — обычные ассоциации. Композиция не обоснована: неизвестно, удаляются ли заявки и сделки вместе с карточкой. Прямая связь Note–Deal отсутствует, поскольку условие не требует создавать сделку из заявки. Агрегаты для этой небольшой модели не выделены.

Подготовка отчёта инициируется руководителем, но размещена в сервисе: процесс читает данные нескольких объектов. По P4 берутся карточки его менеджеров и возвращается текстовый результат. Точное содержание отчёта не выводится из исходного текста.

## Неуточнённые условия

Остаются открытыми совместное ведение карточек несколькими менеджерами, принадлежность заявки/сделки нескольким карточкам, подробные данные и этапы сделки, структура реквизитов, часовой пояс заявки, а также состав, охват и хранение отчёта. Принятые для диаграммы решения перечислены отдельно в [00-source.md](00-source.md); пробелы сценариев — в [07-coverage.md](07-coverage.md).
