# Данные операции и связи классов CRM

Модель содержит пять сущностей и один сервис. Записи коллекций в таблицах обозначают концы ассоциаций: отдельные дублирующие поля с теми же данными не вводятся.

## Атрибуты

| Класс | Атрибут | Тип и кратность | Основание |
| --- | --- | --- | --- |
| ClientCard | id | Identifier [1], неизменяемый | P3, идентичность карточки. |
| ClientCard | requisites | String [1] | R7, представление P6. Конкретные поля реквизитов не заданы. |
| Note | id | Identifier [1], неизменяемый | P3, различение заявок с одинаковым текстом и временем. |
| Note | submittedAt | DateTime [1] | R8, объединяет обязательные дату и время. |
| Note | messageText | String [1] | R8, обязательное значение. Отдельное ограничение на длину текста не задано. |
| Note | replyText | String [0..1] | R9, отсутствие ответа допустимо. |
| Deal | id | Identifier [1], неизменяемый | P3, различение проведённых сделок. Сумма, дата и статус не заданы. |
| SalesManager | id | Identifier [1], неизменяемый | P3, идентичность сотрудника. |
| DepartmentHead | id | Identifier [1], неизменяемый | P3, идентичность руководителя. |
| ReportService | — | Нет хранимых атрибутов | Подготавливает результат по переданному контексту. |

String, DateTime, Identifier, Set и Void — стандартные/условные типы сигнатур, не дополнительные классы предметной области. id не подменяет обязательные реквизиты и содержимое заявки.

## Операции

| Владелец | Сигнатура | Контракт и источник |
| --- | --- | --- |
| ClientCard | ClientCard(requisites: String) | Создание карточки с реквизитами и пустыми notes/deals; R1, R7, P2, P5. Включение в назначения выполняется assignCard. |
| ClientCard | updateRequisites(requisites: String): Void | Заменить реквизиты; R1, R7, P5. |
| ClientCard | addNote(submittedAt: DateTime, messageText: String): Note | Создать новую заявку с обеими обязательными величинами, без ответа, связать с этой карточкой и вернуть; R2, R7–R9, P5. |
| ClientCard | recordDeal(): Deal | Создать отдельную запись о проведённой сделке, связать с карточкой и вернуть; R3, R7, P5. Бизнес-этапы до фиксации результата не заданы. |
| Note | setReply(replyText: String): Void | Установить текст ответа; обязательные данные не меняются; R9. Удаление ответа отдельным сценарием не задано. |
| Deal | — | Самостоятельные изменяющие операции не требуются условием. Создание выполняет ClientCard.recordDeal. |
| SalesManager | assignCard(card: ClientCard): Void | Включить карточку в assignedCards и установить её manager. По P1 карточка не должна быть назначена другому менеджеру. Повторное назначение тому же менеджеру не дублирует связь; R10. |
| SalesManager | assignHead(head: DepartmentHead): Void | Установить единственного руководителя, согласовав обратную роль managers; R11. При замене старый руководитель перестаёт ссылаться на этого менеджера. |
| DepartmentHead | getManagedCards(): Set<ClientCard> | Прочитать managers.assignedCards и вернуть объединение карточек без дубликатов; P4. Не хранит независимую копию этих назначений. |
| ReportService | prepareReport(head: DepartmentHead): String | Прочитать getManagedCards, реквизиты и историю карточек; вернуть отчёт по P4, не изменяя источники. Точная форма и показатели требуют уточнения; R4–R5. |

Чтение атрибутов и переход по связям подразумеваются моделью; отдельные getId/getText/getNotes не добавлены. Видимость «-» в UML означает инкапсуляцию реализации, а не запрет использовать эти данные при реализации отчёта. В программной реализации потребуется интерфейс чтения, но его детализация не нужна для предметной модели.

## Ассоциации

Кратность возле B означает число объектов B для одного объекта A. В колонках ролей указаны имена свойств, ведущих к соответствующему концу.

| Имя связи | Конец A и роль A | Кратность A | Конец B и роль B | Кратность B | Тип и обоснование |
| --- | --- | --- | --- | --- | --- |
| supervises | DepartmentHead, head | 1 | SalesManager, managers | 0..* | Ассоциация. R11: у менеджера один руководитель. Обратная нижняя граница не задана, принято P7. |
| assignedTo | SalesManager, manager | 1 | ClientCard, assignedCards | 2..* | Ассоциация. R10: у менеджера несколько карточек. Число менеджеров карточки неизвестно; 1 выбрано по P1. |
| recordsNotes | ClientCard, card | 1 | Note, notes | 0..* | Ассоциация по R7. Единственность карточки и возможность пустой истории — P2. |
| recordsDeals | ClientCard, card | 1 | Deal, deals | 0..* | Ассоциация по R7. Единственность карточки и возможность пустой истории — P2. |

Все обратные роли — два направления одной связи, а не независимые списки. Правила удаления и общий жизненный цикл не определены, поэтому ромбы композиции и агрегации не используются. Глагол «содержит» здесь означает учёт записей и сам по себе не доказывает композицию.

## Зависимости сервиса

| Имя | Клиент зависимости | Поставщик | Роли и кратности |
| --- | --- | --- | --- |
| selectsScope | ReportService | DepartmentHead | Сервис получает head как параметр и вызывает getManagedCards. Зависимость, не хранимая ассоциация; кратности неприменимы. |
| readsCardData | ReportService | ClientCard | Сервис читает реквизиты и переходит к notes/deals; кратности неприменимы. |
| readsNoteData | ReportService | Note | Сервис читает дату, сообщение и необязательный ответ; кратности неприменимы. |
| readsDealData | ReportService | Deal | Сервис перечисляет записи сделок; подробные поля не определены; кратности неприменимы. |

Кратности UML задают количество связанных экземпляров в ассоциации. Приписывать их зависимостям между классификаторами было бы неверно. Четыре зависимости показаны в итоговой диаграмме; скрытая линия в исходнике, если используется для раскладки, не является предметной связью.

## Преобразование отложенных и отклонённых понятий

| Понятие | Отражение | Владелец или основание исключения |
| --- | --- | --- |
| Реквизиты | requisites: String | ClientCard, R7, P6. |
| Дата и время | submittedAt: DateTime | Note, R8. |
| Текст сообщения | messageText: String | Note, R8. |
| Текст ответа | replyText: String [0..1] | Note, R9. |
| Клиент | Актор ClientActor, его сведения в карточке | Не вводится дублирующий класс Client. |
| Отчёт | Возвращаемое String | ReportService.prepareReport, P4. |
| Управление карточками | ManageClients; создание и updateRequisites | ClientCard. |
| Обработка заявки | ProcessNote; addNote и setReply | ClientCard и Note. |
| Проведение сделки | ConductDeal; recordDeal | ClientCard, полнота бизнес-процесса не определена. |
| Подготовка отчёта | PrepareReport; prepareReport | ReportService. |
| Назначение | assignCard, assignHead; assignedTo, supervises | SalesManager и связанные объекты. |
| ClientCard, Note, Deal как английские обозначения | Уже существующие одноимённые классы | Дубликаты не создаются. |
| Отдел | Самостоятельного элемента нет | Нет собственной ответственности или данных. |
| CRM, система | Граница use-case диаграммы | Не объект внутри предметной модели. |
| Функции, работа, местоимения | Самостоятельного элемента нет | Контекст и отсылки. |

## Ограничения вне кратностей

1. addNote требует submittedAt и messageText. Отсутствующий ответ отличается от присутствующего текста; запрет пустой строки из условия не выводится.
2. assignedCards, managers, notes, deals — множества ссылок без повторного включения одного объекта.
3. Рабочее состояние каждого менеджера удовлетворяет R10–R11: не менее двух карточек и ровно один руководитель. Инициализация назначений находится вне описанных сценариев.
4. Изменение связи согласует обе её роли. Конструктор карточки может создать временно ещё не назначенный объект; завершённый сценарий регистрации включает assignCard и удовлетворяет P1.
5. id неизменяем; два экземпляра Note или Deal с совпадающими предметными данными могут оставаться разными объектами.
6. Отчёт читает данные и не изменяет карточки, заявки, сделки и назначения. По P4 его охват ограничен карточками менеджеров переданного руководителя; это не реализация механизма авторизации.
7. Отсутствует требование, что Deal создаётся из Note. Такая связь не вводится.
