# Типы классов CRM

| Класс | Тип | Основание |
| --- | --- | --- |
| ClientCard | Entity | Две карточки с одинаковыми реквизитами могут быть разными учётными объектами. Изменение реквизитов сохраняет идентичность карточки. |
| Note | Entity | Две заявки с одинаковым текстом и временем не обязаны быть одной заявкой. Добавление ответа не создаёт другую заявку. |
| Deal | Entity | Разные проведённые сделки должны быть различимы даже при совпадении будущих полей. Текущая модель не выдумывает эти поля. |
| SalesManager | Entity | Назначения относятся к определённому сотруднику. Замена карточек или руководителя не меняет его идентичность. |
| DepartmentHead | Entity | Один и тот же руководитель может быть назначен нескольким менеджерам. Изменение команды не создаёт нового руководителя. |
| ReportService | Service | Выполняет подготовку отчёта, не имеет собственного предметного состояния, читает сущности и возвращает результат. |

id из P3 явно показывает идентичность сущностей. Отдельного пользовательского Value-object нет: для реквизитов и текстового отчёта недостаточно заданной структуры; стандартные String и DateTime не разворачиваются в классы модели.

Repository не добавлен: требования не описывают поиск по общему хранилищу, загрузку и сохранение через отдельный интерфейс. Карточка, хранящая историю конкретного клиента, остаётся Entity. Она не становится Repository из-за наличия коллекций Note и Deal.

Factory не добавлен: создание записи в addNote и recordDeal — небольшая операция существующей сущности, не самостоятельная ответственность с вариантами конструирования. Ни создание объектов, ни наличие конструктора не делают класс Factory автоматически.

Подготовка отчёта отделена от состояния сотрудников и карточек. Несовместимых ответственностей, требующих дополнительного разделения классов, при заданной детализации не обнаружено. Все шесть классов проходят правило принятия из 04-criteria.md.
