# 7. Сценарии и проверка покрытия

Исходный текст задаёт структуру. Актор «Специалист по качеству», граница «Схема оценки качества ПС» и действия редактирования/просмотра — проектное дополнение D1. Учебные команды R5–R8 выполняет автор решения; они не становятся функциями разрабатываемой предметной модели.

В 07-use-cases.puml четыре цели: UC1 настроить метрики критерия на этапе, UC2 задать критерии фактора на этапе, UC3 просмотреть схему этапа, UC4 сопоставить анализ и реализацию. Связи include/extend не требуются: наличие данных для просмотра — предусловие, а не обязательный вызов сценария настройки при каждом просмотре.

## Основные сценарии

| Use case → шаг | Класс и операция | Данные и связи | Результат / изменение | Покрытие |
|---|---|---|---|---|
| UC1 → выбрать этап, критерий, несколько метрик | Чтение name выбранных объектов | ЭтапРазработки, Критерий, Метрика; каталог передан в границе D1 | Выбраны существующие определения; отдельный Repository не нужен для концептуальной задачи | Покрыт, D1 |
| UC1 → задать метрики для анализа | stageAnalysis.configureCriterion(stability, {m1, m2}) | stage, criterion, metrics | Создана stabilityAnalysis либо заменено её множество метрик | Покрыт, R3, R9 |
| UC1 → задать метрики для реализации | stageImplementation.configureCriterion(stability, {m1, m2, m3}) | Другая пара (stability, stageImplementation), общие m1/m2 | Создана отдельная stabilityImplementation; анализ не изменился | Покрыт, R3, R6, R10 |
| UC1 → задать метрики работоспособности | stageImplementation.configureCriterion(ability, {m4, m5}) | Настройка abilityImplementation | Второй критерий реализации имеет собственный набор | Покрыт, R10 |
| UC2 → описать надёжность на анализе | stageAnalysis.describeFactor(reliability, {stabilityAnalysis}) | factor, stage, criterionSettings | Создано factorAnalysis с одним критерием | Покрыт, R2, R9 |
| UC2 → описать надёжность на реализации | stageImplementation.describeFactor(reliability, {stabilityImplementation, abilityImplementation}) | Независимое factorImplementation | На реализации два критерия при том же факторе | Покрыт, R2, R6, R10 |
| UC3 → получить факторы этапа | ЭтапРазработки.factors() | factorDescriptions → factor.name | Показаны факторы и их контекстные описания | Покрыт, R1–R2 |
| UC3 → получить критерии и метрики | ОписаниеФактораНаЭтапе.criteria(); для каждой criterionSettings — НастройкаКритерияНаЭтапе.metrics() | criterion.name, metrics → name; навигация по связям | Выведены определения метрик нужного критерия именно на выбранном этапе | Покрыт, R2–R3 |
| UC4 → прочитать обе схемы | factors(), criteria(), metrics() на двух этапах | Общие reliability, stability, m1, m2; разные контекстные объекты | Специалист видит различие наборов: +Работоспособность и +m3 на реализации | Покрыт, R6–R10 |

## Альтернативы и ограничения

| Вариант → шаг | Класс и операция | Данные / результат | Покрытие |
|---|---|---|---|
| R4 → включить общую метрику в другой критерий | configureCriterion(otherCriterion, {m1, anotherMetric}) | Тот же объект m1 входит в две настройки разных критериев; исходная настройка не меняется | Покрыт структурой many-to-many; это проверочный пример, не дополнительное содержание рис. 15 |
| D3 → повторно настроить ту же пару | configureCriterion / describeFactor | Найден существующий объект пары; setMetrics/setCriteria заменяет только его множество | Покрыт контрактом; дубликат запрещён C1–C2 |
| D2 → передать 0 или 1 метрику | configureCriterion / setMetrics | Отказ; прежний набор сохранён | Покрыт контрактом 2..* |
| D2 → передать пустой набор критериев | describeFactor / setCriteria | Отказ; прежний набор сохранён | Покрыт контрактом 1..* |
| D5 → смешать этапы | describeFactor / setCriteria | Настройка анализа не включается в описание реализации; отказ по C3 | Покрыт контрактом |
| D2 → повторить одну и ту же метрику дважды | configureCriterion / setMetrics | Множество содержит только одну различную метрику; отказ | Покрыт C4 и 2..* |
| D6 → получить готовую схему с пропущенной парой фактор–этап | Проверка полноты совокупности описаний | Такая совокупность остаётся черновиком; не считается полной схемой R2 | Покрыт ограничением C6, отдельный use case публикации не придумывается |

Результат измерения не нужен для этих сценариев: картинки задают состав схемы, но не числовые оценки. Никакие альтернативные алгоритмы измерения исходным текстом не заданы.

## Журнал после черновика

1. Проверка сценариев не выявила необходимости в новых классах: оба связывающих класса уже включены и прошли этапы 1–5.
2. В итоговой диаграмме классов добавлены стереотипы Entity по этапу 8 и развёрнуты ограничения C1–C7. Состав атрибутов, методов и связей черновика сохранён; скрытых изменений модели нет.
3. Этап 9 не вводит агрегаты. Поэтому пути доступа и операции сценариев не изменяются. Повторная проверка приведённой таблицы даёт то же покрытие.
4. Диаграммы экземпляров раздельно фиксируют два этапа; одинаковые aliases reliability, stability, m1, m2 означают одни и те же определения, а не их копии.

Неразрешённых пробелов относительно задачи 5.3 нет. Выбор изменяемого интерфейса, идентичности и нижних границ явно указан в D1–D6; расширения до реального вычисления качества потребовали бы новых требований.
