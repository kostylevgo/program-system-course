# Задача 5.3. Оценка качества программных средств

Источник: [image.png](../image.png), страница 39 и фрагмент следующей страницы. Решается только задача 5.3, включая пункты а–г. Нормативные положения за пределами приведённого условия не привлекаются.

## Исходный текст

> 5.3. В межгосударственном стандарте по оценке качества программных средств ГОСТ 28195—89 качество характеризуется набором факторов. Краткое описание: на каждом из этапов разработки программного средства фактор описывается набором критериев. Каждый критерий измеряется с помощью нескольких метрик, различающихся для этапов разработки. Метрики могут использоваться разными критериями.
>
> а. Выделите классы, применив метод именных групп к краткому описанию из условия задачи.
>
> б. Уточните отношения между классами, учитывая, что на разных этапах разработки факторы описываются разными наборами критериев, которые измеряются различными метриками.
>
> в. На рис. 14 представлена схема критериев и метрик качества для фазы анализа. Покажите ее представление в модели на диаграмме экземпляров.
>
> г. Используя схему, представленную на рис. 15, постройте критерии и метрики надежности для этапа реализации программного средства.

## Нумерованные требования

| Код | Требование |
|---|---|
| R1 | Качество программного средства характеризуется набором факторов. |
| R2 | На каждом этапе разработки фактор описывается набором критериев. |
| R3 | Каждый критерий измеряется несколькими метриками; набор зависит от этапа разработки. |
| R4 | Одна метрика может использоваться разными критериями. |
| R5 | Пункт а: выделить классы методом именных групп. |
| R6 | Пункт б: выразить зависимость обоих наборов — критериев и метрик — от этапа. |
| R7 | Пункт в: представить рисунок 14 для анализа диаграммой экземпляров. |
| R8 | Пункт г: построить критерии и метрики надёжности для реализации по рисунку 15. |
| R9 | Рисунок 14: «Надежность ПС» → «Устойчивость функционирования» → метрики 1 и 2. |
| R10 | Рисунок 15: «Надежность ПС» → «Устойчивость функционирования» → метрики 1, 2, 3; тот же фактор → «Работоспособность» → метрики 4, 5. |

Названия метрик на рисунках:

1. Средства восстановления при ошибках на входе.
2. Средства восстановления при сбоях оборудования.
3. Реализация управления средствами восстановления.
4. Функционирование в заданных режимах.
5. Обеспечение обработки заданного объема информации.

Номера 1–5 — обозначения метрик на рисунках, а не результаты измерений.

## Проектные предположения

- D1. Для этапов 3 и 7 метода Аббота рассматривается инструмент составления и просмотра схемы оценки качества. Актор «Специалист по качеству» и операции настройки/просмотра введены как проектное дополнение: условие задаёт структуру, но не интерфейс системы. Расчёт оценок, формулы, шкалы и измеренные значения не заданы и не добавляются.
- D2. Набор критериев в готовом описании непустой (1..*); «несколько метрик» читается буквально как не менее двух (2..*). Все наборы — множества без повторов.
- D3. Для каждой пары (фактор, этап) существует не более одного описания; для (критерий, этап) — не более одной настройки метрик. При совместном использовании критерия несколькими факторами на одном этапе его набор метрик общий: зависимость от фактора в условии не задана.
- D4. Факторы, критерии, метрики и этапы имеют устойчивую смысловую идентичность; name — отображаемое имя, а не ключ. Одинаковые метрики 1 и 2 на двух рисунках — те же объекты. Идентификаторы объектов на UML-диаграммах не являются дополнительными полями классов.
- D5. Ключевые ссылки (фактор/критерий и этап) после создания неизменяемы. Изменение множества выполняется атомарно с проверкой ограничений. Общий жизненный цикл объектов не задан, поэтому все структурные связи — обычные ассоциации.
- D6. В процессе составления схемы допустимы ещё не используемые элементы и этапы; отсюда обратные кратности 0..*. Готовая схема обязана содержать ровно одно описание каждого рассматриваемого фактора на каждом рассматриваемом этапе (R2). Область рассматриваемых факторов и этапов задаётся задачей, а не отдельным классом «Система».

Эти предположения отделены от исходных требований и последовательно используются во всех файлах.
