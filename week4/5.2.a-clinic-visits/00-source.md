# Задание 5.2. Учёт посещений поликлиники

## Исходный текст

> 5.2. Больной посещает доктора, чтобы получить рецепт на лекарства для своей болезни.
> а. Применив метод Аббота, выделите классы и постройте модель предметной области для
> системы учета посещений больными докторов для поликлиники.

## Требования из текста

| Код | Требование | Основание |
| --- | --- | --- |
| R1 | Больной посещает доктора. | «Больной посещает доктора» |
| R2 | Цель посещения — получить рецепт на лекарства для болезни больного. | «чтобы получить рецепт на лекарства для своей болезни» |
| R3 | Модель относится к системе учёта посещений больными докторов для поликлиники. | «системы учета посещений больными докторов для поликлиники» |
| R4 | Выделить классы методом Аббота и построить модель предметной области. | «Применив метод Аббота, выделите классы и постройте модель» |

R4 определяет способ выполнения задания, а не функцию поликлиники. R1–R3 не задают интерфейс программы, точные кратности, справочники и правила хранения.

## Проектные допущения

| Код | Принятое допущение |
| --- | --- |
| A1 | Рассматривается одна поликлиника и один её логический реестр посещений. Поликлиника — граница модели. |
| A2 | У посещения ровно один пациент, один доктор и одна учитываемая болезнь. У пациента и доктора может быть от нуля до любого числа посещений. Повторная встреча той же пары является отдельным посещением. |
| A3 | У посещения может быть 0..* рецептов; каждый рецепт относится ровно к одному посещению и содержит 1..* непустых названий лекарств. Ноль рецептов допустим до выписки; после успешной выписки появляется новый рецепт. Верхний предел числа рецептов текстом не установлен; `*` — принятое отсутствие ограничения. |
| A4 | Пациент, доктор, посещение и рецепт имеют стабильные идентификаторы. У пациента и доктора хранится ФИО, у посещения — дата и время. Совпадение ФИО или содержимого записей не означает совпадение объектов. |
| A5 | Болезнь и лекарства представлены непустыми строками с названиями. Ведение справочников, кодирование диагнозов, дозировки, количество упаковок и схемы приёма не заданы. |
| A6 | Данные в систему вводит доктор. Учёт конкретизируется регистрацией посещения и получением истории посещений выбранного пациента. Доступ пациента к интерфейсу системы не предполагается. |
| A7 | Зарегистрированные записи сохраняются в логическом реестре. Удаление, изменение завершённых записей и физический способ хранения вне рассматриваемых сценариев. Перед регистрацией уже выбраны существующие пациент и доктор; ведение их карточек не моделируется. |

Это допущения учебной модели, а не извлечённые из текста дополнительные требования. Операции не описывают медицинские правила выписки действительного рецепта.

## Порядок чтения результата

Файлы `01`–`09` соответствуют девяти этапам навыка. `06-draft.puml` сохраняет черновик до проверки сценариев. `07-coverage.md` фиксирует обнаруженный пробел учёта и его исправление. Итог — `final-class-diagram.puml`.

## Границы определённости

В исходном условии не определены: несколько болезней за посещение, предельное число рецептов, состав лекарственного назначения, пользователь системы и правила исправления записей. Для данного решения применяются A1–A7. Если эти границы изменятся, потребуется пересмотреть атрибуты, кратности и выделение классов Болезнь/Лекарство.
